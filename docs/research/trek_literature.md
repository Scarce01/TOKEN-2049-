状态：2026-10-06。每条标了我读到了什么：**[原文]** 读了论文正文；**[摘要]** 只读了摘要或网页摘录；**[搜索]** 只看了搜索结果。数字都是论文自己报告的，不是我们复现的。

## 1. 污点传播方法

来源：Tironsakkul 等，*Probing the Mystery of Cryptocurrency Theft*（[arXiv 1906.05754](https://arxiv.org/abs/1906.05754)）[原文]。**注意：只针对比特币 UTXO。**

| 方法 | 规则 | 论文给的例子（7 BTC 干净 + 3 BTC 污点输入，输出 9 和 1） | 优缺点（论文原意） |
| --- | --- | --- | --- |
| Poison | 有污点输入，所有输出全算污点 | 两个输出都算污点，污点从 3 BTC 变成 10 BTC | 过度，只适合当基线 |
| Haircut | 每个输出按输入占比分到污点 | 9 BTC 输出带 2.7 污点，1 BTC 输出带 0.3 | 比 Poison 实用，但混合越多，被标记的交易和地址越多，不适合追踪 |
| FIFO | 先进先出，按顺序分配 | 第一个输出带 2 BTC 污点，第二个带满 1 BTC | 更精确，但「交易顺序可以被用户任意安排」，用户可以颠倒顺序来误导 FIFO |
| LIFO、TIHO | LIFO 反过来；TIHO 把污点输入优先分给金额最大的输出 | | 论文新提出，意在识别窃贼的躲避策略 |

- 论文的结论是**各种方法得出的结果差异很大**，且「还需要进一步验证才能真正衡量追踪准确度」，只测了两个被盗案例。**没有给出哪个方法最准。**
- **对我们的架构**：
  - 我们用的是按时间顺序的 Haircut，不是 UTXO 版的。以太坊是账户模型，没有「输入输出对应」，所以这些定义只能类比。
  - FIFO 的弱点（攻击者可以先存入干净的钱，让污点被排到后面）有论文原文支持。
  - **待做**：用缓存的 Bybit 数据加一个 FIFO 对照回测，量化差多少。

## 2. 交易所充值地址识别

来源：Victor，*Address Clustering Heuristics for Ethereum*（FC 2020，[PDF](https://www.ifca.ai/fc20/preproceedings/31.pdf)）[原文]。

- **规则**：充值地址收到钱后，在一段时间内把几乎全部转给一个大交易所地址（转出略少于收到，差额是手续费）。识别依赖两个参数：最大金额差 amax、最大时间差 tmax。
- **参数**：先用宽松值（1 ETH、10,000 区块）取样，再按经验分布的第 95 百分位收紧：**amax = 0.01 ETH（经验值 0.0083）、tmax = 3,200 区块（经验值 3,185，约 13 小时）**。代币的 amax 取 0，因为代币不能付手续费。
- **过滤**：排除已知交易所地址；充值地址只能转给**一个**交易所地址；只看既不是已知交易所、也没挖过矿的外部账户。
- **规模**：13,104,448 条转发轨迹；6,670,392 个充值地址对应 186 个交易所地址；总共能聚类 17.9% 的活跃外部账户。
- **已知弱点**：攻击者可以伪造（收到钱后向已知交易所转同样金额，就会被当成充值地址）；只看了一层转发；**没有真实标注数据，没法评估质量**。
- **对我们的架构**：
  - Trek 要判断「钱到了哪家交易所」，这就是方法。
  - **13 小时的窗口是回溯用的**，实时场景里充值地址要等它转发出去后才被认出来，会有滞后。对策：同时维护交易所自己的已知充值合约（论文提到 Kraken 部署了大量相同字节码的充值合约，可以直接按字节码认）。
  - 只有**成员交易所**才能在链上强制；非成员只能通知。

## 3. 跨链配对

### 3.1 ConneX（[arXiv 2511.01393](https://arxiv.org/abs/2511.01393)）[原文]

- **配对用五元组**：目的地址、目标链、代币类型、金额、时间戳。规则：目的地址一致、代币一致、金额差 / 源金额 ≤ fee_rate（取 **20%**）、时间差 ≤ time window（取 **2 小时**）、目标链和源交易声明的目的链一致。
- 参数扫描：fee_rate ≥ 0.15 且 time window ≥ 3,600 秒时 F1 稳定在 0.96 以上。
- 五个桥：Stargate、DLN、Multichain、Celer、PolyNetwork，约 50 万笔交易。

| 桥 | 精确率 | 召回率 | F1 |
| --- | --- | --- | --- |
| Stargate | 0.9972 | 0.9923 | 0.9948 |
| DLN | 0.9981 | 0.8653 | 0.9270 |
| Multichain | 0.9986 | 0.9714 | 0.9848 |
| Celer | 0.9984 | 0.9682 | 0.9831 |
| Poly | 0.9862 | 0.9754 | 0.9807 |
| 整体 | 0.9957 | 0.9545 | 0.9746 |

- 对比基线的 F1：按时间顺序 0.0014、只用大模型 0.7064、规则法（Connector，只覆盖 3 个桥）0.7741、SBERT 相似度 0.5676、规则加相似度 0.6010。
- 限制：需要路由合约的 ABI（约 80% 的桥合约开源）；只支持 EVM；每边一笔交易。

### 3.2 SoK: Cross-Chain Transaction Identification and Matching（[arXiv 2608.17532](https://arxiv.org/abs/2608.17532)）[摘录]

- 三类机制：**确定性标识符匹配**（链上事件里的 srcTxHash、deposit_id、消息编号）、**字段约束启发式**（金额、时间、地址的容差窗口）、**模型辅助匹配**。
- 可靠性排序：链上标识符最可靠（Jigsaw 报告在 13 个桥上匹配率 99.8%），启发式其次（CONNECTOR 95.95%，金额容差 0.5% 到 20%，存款的时间窗口 5 到 24.2 分钟），模型辅助再次（ABCTRACER F1 91.75%，在没见过的桥上 93.95%）。
- 失败模式：没有标识符时退回弱证据；每个桥字段不同要手写规则；未配对的交易既可能是攻击，也可能是数据缺口。
- 开放问题：n 对 m 的配对（聚合器、流动性池）、未配对怎么解读、缺少共享基准。
- **没有给 Stargate、Across 的具体做法。**

### 对我们的架构
- 比赛里只需要覆盖 **Stargate 和 Across** 两个桥：写**确定性的事件解析器**（读桥合约事件里的标识符），失败再退回金额加时间窗口。ConneX 的 0.7741 说明纯规则在多桥场景下不够，但我们只做两个桥，不需要大模型。
- 回退规则的金额容差：ConneX 用 20% 是为了覆盖各种手续费；实时追踪应该用更紧的值（先试 1% 到 2%），**未配对的一律当「未知」，不当「干净」**。
- 这直接对应 Bitget 回测里卡住的 6 个钱包（经 Stargate 和 Across 转入）。

## 4. 语义分析：看懂 DeFi 里的资金去向

来源：AMLGuard，*Tracing the Shadows*（[arXiv 2607.18869](https://arxiv.org/abs/2607.18869)，2026 年 7 月预印本）[原文]。

- **流程**：从已知黑客地址出发，迭代深度优先。每笔交易：构建 Token Flow Graph → 推断 DeFi 语义 → 恢复跨链意图 → 更新账户状态 → 扩展追踪前沿；到交易所或混币器停止。
- **语义单元 DSU** 覆盖五种操作：Approve、Transfer、Swap（含流动性）、Deposit、Withdraw。
- **分工**：规则法处理约 **77%** 的交易，检索增强的大模型处理其余约 **23%**。
- **效率**：每个案例 476.2 秒（单链）和 399.7 秒（跨链）；每笔交易 1.6 秒和 1.4 秒；大模型成本约 0.007 美元一笔。
- **评估**：82 个真实案例、超过 10 亿美元，目的地精确率 94.4%（单链）和 87.6%（跨链）；地址召回率 98.4% 和 95.8%。标注来自 CertiK、Beosin、SlowMist、BlockSec、SharkTeam 的洗钱报告，由三位作者各自重建路径再合并。
- **明确是事后分析**，不是实时。
- **限制**：追不了进入混币器之后的资金；**账户模型的歧义**：「黑客的钱进入一个本来就有正常资产的账户后，之后转出的钱无法明确判定是不是赃款」；跨链意图恢复在部分代理合约上失败（成功率 94.6%）；没有做反向传播；只看单笔交易，不看多笔组合的 DeFi 流程；不追交易所内部。
- **对我们的架构**：
  - 我们的「兑换感知」相当于它的 Swap、Deposit、Withdraw 的子集，规则法就够了。
  - **它承认的「账户里有正常资产就无法区分」，正是我们那 3 个误封钱包的同一类问题**，所以这不是我们的实现缺陷，而是账户模型的本质限制。
  - 它每笔 1.6 秒的量级，说明实时追踪的瓶颈不在算法，而在数据读取和 CRE 的读取预算。
  - 它是事后分析，**这正是我们实时追踪能占的空位**。

## 6. 映射到架构：每个部件取什么、不取什么

| 部件 | 取自 | 决定 |
| --- | --- | --- |
| 数据摄入 | Bitquery 流、我们自己的 Etherscan 缓存 | 每个新区块增量读取；规则法（毫秒级），不用大模型 |
| 传播 | 我们的时间顺序 Haircut；论文 1 | 保持；**补 FIFO 对照回测** |
| 兑换 | AMLGuard 的 Swap、Deposit、Withdraw | 已有兑换感知，够用 |
| 出口识别 | Victor 的充值地址规则；Kraken 式相同字节码合约 | 先用已知标签加充值合约字节码，再加 Victor 的转发规则（amax 0.01 ETH、tmax 3,200 区块是以太坊主网的经验值，要重新校准） |
| 跨链 | SoK 的可靠性排序；ConneX 的五元组作为回退 | Stargate、Across 写确定性事件解析器；回退用紧容差；未配对记「未知」 |
| 置信度与动作 | 我们 docs/47 的风控框架 | 衍生条目最多触发**延迟**，不做硬冻结（见云端原型审查） |
| 评估 | 我们已有三个案例 | 指标：钱到达出口之前多少分钟被标记；误拦数。加一个「拆小额」场景 |

## 7. 还没解决的问题

1. 以太坊账户模型的「干净资产混合」问题：没有已知的完美解，AMLGuard 自己也承认。
2. Victor 的参数是 2015 到 2019 年的主网数据校准的，今天的交易所充值行为可能变了。
3. 实时场景里的「历史」判断（新钱包还是老钱包）需要读 nonce 或历史交易数，要算进 CRE 的读取预算。
4. 摘要级别的来源（Yousaf、trans2vec、Elliptic）需要读正文后才能引用具体数字。
